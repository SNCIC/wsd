# 基础资料同步清单（金蝶云星空账套）

> 目的：把「所有基础资料都要同步」变成一份**有出处、有顺序、有边界**的清单。
> 每个 formId、每个字段名、必录与否都来自账套字段主索引
> `odoo-kingdee/data/kingdee-openapi/fields_master.csv`（账套优先），
> 接口与操作来自 `kingdee_api_catalog.csv`。核对于 2026-10-13。
>
> 工序见 `kingdee-接入SOP.md`：每接一个对象 = 一条控制台数据 + 一个方法 + `SYNC_METHODS` 一行。
> 代码量不大，**成本在每一步真连账套的对齐与试推**（元数据标必录 ≠ WebAPI 可写）。

## 1. 范围：先收敛，再动手

| 口径 | 对象数 | 说明 |
| :--- | ---: | :--- |
| 官方子系统 = `基础资料` | 44 | 最窄的一组 |
| `BD_` 前缀 + 对象 type 400 | 56 | 物料、客户、供应商、单位、币别、部门、仓库… |
| 全领域 type = 400（主数据） | 835 | 含 PLM / ENG / CMK / CRM / DRP 等各子系统的主数据 |
| 账套里真实有字段的主数据 | 857 | 上表口径加上 `ORG_`/`CN_`/`FIN_`/`BAS_` 前缀 |

**835 个不可能也不该全做。** 决定范围的不是对象类型，而是**引用链**：后面要接的单据
（采购订单、采购入库、销售订单…）会引用谁。所以按下表的「被引用次数」排序——它统计的是
**有多少个其他对象的字段指向它**，引用多的必须先在，否则单据里的引用字段填不出来。

## 2. 现状：已实现

控制台 `Kingdee → Synchronization`，调度见 `models/kingdee_sync_target.py` 的
`SYNC_METHODS`，键是 **(方向, 金蝶对象)**——不是 Odoo 模型：客户与供应商共用
`res.partner`，两个方向必须落到两个方法上。

| 金蝶对象 | Odoo 模型 | 方向 | 读写字段 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| `BD_MATERIAL` 物料 | `product.template` | 双向 | 组织、编码/名称、7 个单位、属性/类别/分组 + 20 项账套固定值；入站加规格/批次/类别 | 被引用 971，账套必录 35 |
| `BD_Customer` 客户 | `res.partner` | 双向 | 组织、编码/名称、结算币别、销售员、销售部门；入站写 `customer_rank` | 被引用 316，账套必录 6 |
| `BD_Supplier` 供应商 | `res.partner` | **仅入站** | 编码/名称、禁用状态、结算币别；入站写 `supplier_rank` | 被引用 312，账套必录 8 |
| `BD_Currency` 币别 | `res.currency` | **仅入站** | 货币代码（ISO）、名称、符号 | 被引用 766，账套必录 4 |
| `BD_Department` 部门 | `hr.department` | **仅入站** | 编码、名称 | 被引用 577，账套必录 3 |
| `BD_UNIT` 计量单位 | `uom.uom` | **仅入站** | 编码、名称、换算（参考单位 + 换算比） | 被引用 **1669**（最高），账套必录 3 |

供应商之所以「仅入站」：出站 payload 还没在账套上做实推验证（`docs/kingdee-接入SOP.md`
第 6、7 步），控制台里那一行已登记但点不动。**在补上之前，先把「伙伴一律当客户推送」的
老行为修掉了**——本库 1232 个伙伴里有 831 个是纯供应商，按老逻辑会被写成 831 条
`BD_Customer`。

### 客户与供应商为什么不共用一套字段

账套对客户与供应商**分别编号**，Odoo 用同一个模型承载两种角色，所以伙伴身上有两套金蝶字段，
由 `_kingdee_form_fields` 按对象声明：

| 金蝶对象 | 编码 | 名称 | 状态 | 最近同步 | 消息 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `BD_Customer` | `kingdee_number` | `kingdee_name` | `kingdee_sync_state` | `kingdee_last_sync_at` | `kingdee_sync_message` |
| `BD_Supplier` | `kingdee_supplier_number` | `kingdee_supplier_name` | `kingdee_supplier_state` | `kingdee_supplier_last_sync_at` | `kingdee_supplier_message` |

两个编码各有唯一约束。控制台的「已对接 / 待推送」也按对象取值
（`_kingdee_target_domain()` + `_kingdee_field()`），所以客户那一行不会再把供应商算进去。

## 4. 已核实的边界（这些是踩过的，别再试）

1. **存货类别不建模型**：`BD_MATERIAL.FCategoryID` 指的是「存货类别」
   （`CHLB05_SYS` 产成品 / `CHLB03_SYS` 自制半成品…），而 Odoo 现有 508 个
   `product.category` 镜像的是**物料分组**（`C.01.101(单相电子式电能表(出口-781))`，名字由
   `<分组编号>(<分组名>)` 组成）。两者是不同维度，若把存货类别也塞进 `product.category`，
   一个目录里会混进两套命名。存货类别目前作为产品上的参考字段
   （`kingdee_category_number` / `kingdee_category_name`）保留。
   物料分组本身**不是独立业务对象**（账套接口里只有 `BD_MATERIAL` 的
   `GroupSave/QueryGroupInfo/GroupDelete` 分组操作），所以也不单独同步。
2. **`BD_UNITGROUP` 在字段索引里 0 个字段**，但 `BD_UNIT.FUnitGroupId` 引用它。
   同步单位时必须现场查组别（`FUnitGroupId.FNumber` 可查），不能靠离线索引。
3. **`BD_Saler` 没有 `Save` 操作**（只有 `BatchSave`），而客户又必填 `FSELLER`：
   销售员只能从金蝶读进 Odoo，不能反过来由 Odoo 创建。
4. **`BD_Currency.FRoundType` 是舍入「模式」**（枚举 `1=四舍五入`、`4=四舍六入五双`），
   不是 Odoo 的舍入「增量」（`res.currency.rounding`）。两者不是同一件事，所以不映射；
   `FAMOUNTDIGITS`（金额精度）与 `res.currency.rounding` 的关系待定，也没映射。
   `FSYSMBOL`（货币符号）是**必读**的：Odoo 19 里 `res.currency.symbol` 是 NOT NULL，
   不读它建不出币别（实测报 `NotNullViolation`）。
5. **`BD_Supplier` 8 个必录里有 4 个在子实体 `FLocationInfo`**（地点名称/地址/手机/联系人）。
   SOP 第 4 条坑说过：子实体的必录在**整个子实体不传**时不触发。本账套客户侧的同类字段
   （`FTTel`）已实测不强制，供应商侧**尚未实测**——这正是它出站还标着「未实现」的原因。
6. **组织机构建议只做只读映射**：把金蝶组织同步成 Odoo 公司会牵动多公司配置，风险与收益不成比例。
7. **Odoo 19 的 `uom.uom` 没有「单位类别」**（旧版的 `category_id` 已移除）：一个单位要么独立
   （`relative_factor` = 1），要么挂在参考单位上（`relative_uom_id` + `relative_factor`，「Contains」）。
   金蝶的「单位组」正是这个结构，所以**不去造 `uom.category`**，而是把组内换算重建成链条。
   约束：没有参考单位的记录，`relative_factor` 必须为 1，否则报「Reference unit of measure is missing」。
8. **Odoo 自带 82 个单位，其中已经有本账套的 `只`、`V`、`mV`、`A`、`m`**（`mV → V` 的换算链本来就存在）。
   所以单位按**名称认领**——名称是单位在 Odoo 里的身份，编码是金蝶的（与币别按 ISO 码认领同理）。
   由此有一条硬规则：**只添加金蝶声明的换算，绝不拆散 Odoo 已有的换算**；把一个「金蝶里独立」的单位
   清成无参考，会悄悄改变 Odoo 里两个单位之间的换算。
9. **物料 payload 的单位是三级取值，顺序是「最具体的先」**（`_kingdee_unit()`）：
   物料自身的 `kingdee_unit_number`（金蝶回读的真实值）→ 产品自身单位的金蝶编码 → 设置页。
   **物料级必须优先**：让产品单位抢先，会在下次推送时**改掉已存在物料的单位**，而金蝶对已有
   业务的物料会拒绝改基准单位。前两级为空时行为与改动前**完全一致**（实测 11558 个产品的
   payload 零差异）。`FPrecision`（小数精度）与 `FRoundType`（舍入模式）都不映射：Odoo 的
   rounding 由 `decimal.precision` 计算，没有可写之处。

## 5. 方向策略

金蝶是账套数据的权威源，Odoo 不该反向创建基础资料：

| 方向 | 对象 |
| :--- | :--- |
| **仅入站** | `BD_Currency`、`BD_Department`、`BD_UNIT`、`ORG_Organizations`、`BD_STOCK`、`BD_Empinfo`、`BD_Saler`、`BD_BatchMainFile`、`BD_TaxRate`、`BD_PaymentCondition`、`BD_RecCondition`、`BD_BANK`、`CN_BANKACNT` |
| **双向** | `BD_MATERIAL`、`BD_Customer`、`BD_Supplier`、`BD_MATERIALCATEGORY`（参考字段） |

控制台只声明策略允许的行：入站对象没有 `out` 行，反之亦然。**依赖按需增加**——
目前只加 `hr`（部门用），仓库落地时才加 `stock`，会计科目类落地时才加 `account`。
模型还不能用的对象（`BD_STOCK` 等）先列在本文件，不写进
`data/kingdee_sync_targets.xml`，这样「加一行」永远不会顺手拖进一个应用。

## 6. 复现这份清单

```bash
# 账套里真实有字段的主数据（对象数）
python tmp/kd_basedata_inventory.py          # 本仓库 tmp/ 下的临时脚本
# 某个对象的必录、操作与引用
python odoo-kingdee/tools/kingdee_fields.py must BD_Supplier
python odoo-kingdee/tools/kingdee_catalog.py ops  BD_Supplier
python sn_wsd_kingdee/tools/probe_form.py BD_Supplier   # 同时给 payload 骨架
```

被引用次数由 `fields_master.csv` 的 `引用对象` 列统计得出（`tmp/kd_refcounts.py`）。
